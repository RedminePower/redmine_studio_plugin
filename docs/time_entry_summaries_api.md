# Time Entry Summaries API

作業時間を「人×作業日×プロジェクト」ごとに要約し、区切りごとの要約値を返す API。

Redmine Studio は作業時間を手元に持っておき、表示した日の要約値を本 API で聞いて、手元の要約値と違う区切りだけ作業時間を取り直す。標準の作業時間の API では「どの日が変わったか」（更新・削除・付け替え）が分からないため、本 API で見分ける。

標準の `TimelogController` を継承した専用コントローラで、絞り込み・見える範囲・Redmine の版の違いは本体に任せている。記録の表は持たず、問い合わせのたびに今の作業時間から計算する。

## エンドポイント

| エンドポイント | 説明 |
|---------------|------|
| `GET /time_entry_summaries.json` | 要約の一覧を取得（JSON） |
| `GET /time_entry_summaries.xml` | 同上（XML） |

## 権限

認証は必須で、匿名アクセスは 401 で拒否します。認証済みユーザに対する権限と見える範囲は、標準の作業時間の一覧（`GET /time_entries`）と同じです（`view_time_entries`。見えないプロジェクトの区切りは返らず、「自分の作業時間だけ」の権限もそのまま効きます）。

## パラメータ

標準の作業時間の一覧と同じ絞り込みを受け付けます。知らない引数は無視します。

| パラメータ | 必須 | 説明 |
|-----------|------|------|
| `from` | ○ | 作業日の開始（`YYYY-MM-DD`） |
| `to` | ○ | 作業日の終了（`YYYY-MM-DD`。この日を含む） |
| `user_id` | | ユーザー ID。`\|` で区切って複数指定できる（例: `1\|2\|3`）。`me` も使える |
| `project_id` | | プロジェクト ID または識別子 |

- `from`・`to` の期間は 62 日まで（`from` と `to` を含めて数える）
- `user_id` に並べられるのは 100 人まで
- 保存したクエリ（`query_id`）は使いません（期間の絞り込みが `from`・`to` から外れるため）
- ページには分けず、一度にすべて返します

### エラー

次のときは 422 で `errors` を返します。

- `from` または `to` が無い、`YYYY-MM-DD` の形でない、ありえない日付
- `to` が `from` より前
- 期間が 62 日を超える
- `user_id` が 100 人を超える

```json
{ "errors": ["the period must be 62 days or less"] }
```

## レスポンス

作業時間が 1 件以上ある区切りだけを返します。並び順は `user_id`・`spent_on`・`project_id` の順です。

```json
{
  "time_entry_summaries": [
    { "user_id": 1, "spent_on": "2026-11-10", "project_id": 3, "digest": "6fff726a84540129ba294270c31f5d6b" },
    { "user_id": 1, "spent_on": "2026-11-11", "project_id": 3, "digest": "2b147f24c76845f8e98ef8b7491e6b8c" }
  ]
}
```

```xml
<time_entry_summaries type="array">
  <time_entry_summary>
    <user_id>1</user_id>
    <spent_on>2026-11-10</spent_on>
    <project_id>3</project_id>
    <digest>6fff726a84540129ba294270c31f5d6b</digest>
  </time_entry_summary>
</time_entry_summaries>
```

| フィールド | 型 | 説明 |
|-----------|-----|------|
| `user_id` | integer | ユーザー ID |
| `spent_on` | string | 作業日（`YYYY-MM-DD`） |
| `project_id` | integer | プロジェクト ID |
| `digest` | string | 区切りの要約値。中身に意味は無く、同じかどうかだけを比べる |

## 要約値の決まり

要約値は、区切りの中の作業時間の次の値から作ります（DB では SUM・COUNT・MAX だけを使う）。

- 件数
- 時間の合計（小数第 2 位で丸める）
- 最大の更新日時
- チケットの番号の合計
- 作業分類の番号の合計

| 変化 | 要約値 |
|------|--------|
| 作業時間を足す・消す | 件数が変わる。区切りの最後の 1 件を消すと、区切りごと返らなくなる |
| 作業時間を直す | 更新日時が変わる |
| チケットを消して作業時間を別のチケットへ付け替える | チケットの番号の合計が変わる |
| 作業分類を消して別の分類へ付け替える | 作業分類の番号の合計が変わる |
| チケットを別のプロジェクトへ移す | 元のプロジェクトの区切りが変わる（または消える）、移した先の区切りが変わる（または増える） |
| 権限が変わって見える作業時間が変わる | 見える作業時間から計算し直すので変わる |

次の場合は要約値が変わらず、拾えません。どちらもまれで、クライアント側で取り直す手段（再読込など）を持つ前提です。

- 更新日時を変えずに、コメント・カスタムフィールドだけをまとめて書き換えたとき
- チケットの番号を入れ替えて、合計が同じになったとき

計算のしかたは後の版で変えることがあります。クライアントは要約値を保存しても構いませんが、値の中身を解釈しないでください。

## 性能

`time_entries` に索引は足していません。作業時間 40 万件のデータで、1 人×8 日の問い合わせは数十ミリ秒で返りました（本体の `user_id` の索引が効きます）。
